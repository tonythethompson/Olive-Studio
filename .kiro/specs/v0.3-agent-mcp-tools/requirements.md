# Requirements Document

## Introduction

Five new MCP tools that close the knowledge gaps identified in `docs/v0.3-agent-gaps.md` for the autonomous optimization agent. These tools form the plan-execute-observe-diagnose-compare loop that allows the agent to operate without human intervention between optimization iterations. All tools are Python functions in `olive-mcp-server/olive_mcp_server/tools/`, lazy-imported via `_TOOL_IMPORTS` in `mcp_server.py`, and registered in `allowedTools.ts` on the Express side.

## Glossary

- **MCP_Server**: The Python FastMCP stdio server (`olive-mcp-server/`) that exposes tools to AI coding agents via the MCP protocol
- **Studio_Bridge**: The loopback HTTP client (`studio_loopback.py`) that calls Olive Studio's Express API over `127.0.0.1` only
- **UIState_Patch**: A partial `UIState` object containing only the fields the agent wants to change (merged onto the full store by the frontend)
- **Job_Registry**: Olive Studio's in-memory registry of optimization jobs, accessed via `GET /api/olive/jobs` and `GET /api/olive/agent/status/:jobId`
- **Agent_Policy**: The `AgentAccessPolicy` resolved from Studio settings that gates submission (`allowJobSubmission`) and cancellation (`allowJobCancellation`)
- **Recipe**: A complete Olive optimization configuration JSON generated by the recipe builder from a UIState
- **KB_Entry**: A knowledge-base troubleshooting entry in `troubleshooting.json` or `studio_troubleshooting.json` with `matched_entry` id, patterns, root cause, workaround, and optional `updated_config`
- **Merge_Patch**: RFC 7386 JSON Merge Patch — null removes a key, non-null sets/overrides
- **Terminal_State**: A job status in `{"completed", "failed", "cancelled"}` — polling stops once reached
- **HF_API**: The Hugging Face public model metadata API at `https://huggingface.co/api/models/{id}`
- **Tool_Import_Registry**: The `_TOOL_IMPORTS` dict in `mcp_server.py` that maps tool names to lazy `(module_path, attribute)` tuples
- **Allowed_Tools_Set**: The `ALLOWED_MCP_TOOL_NAMES` Set in `src/server/services/mcp/allowedTools.ts` that controls which tools the Express proxy accepts

## Requirements

### Requirement 1: execute_and_observe Tool — Job Submission

**User Story:** As an autonomous agent, I want to submit a recipe and observe the job to completion, so that I can iterate on optimization without human polling.

#### Acceptance Criteria

1. WHEN a recipe JSON that passes Studio's `/api/olive/jobs/submit` schema validation and an optional timeout between 10 and 1800 seconds are provided, THE MCP_Server SHALL submit the recipe to Studio via `POST /api/olive/jobs/submit` through the Studio_Bridge
2. IF the recipe JSON is malformed or fails schema validation at Studio, THEN THE MCP_Server SHALL return a structured error with code `"invalid_recipe"` and a message indicating the validation failure reason without submitting a job
3. IF the Agent_Policy does not have `allowJobSubmission=true`, THEN THE MCP_Server SHALL return a structured error with code `"submission_denied"` and a message explaining the policy requirement
4. IF Studio is unreachable or `OLIVE_STUDIO_API_URL` is unset, THEN THE MCP_Server SHALL return a `studio_unavailable` error without crashing
5. WHEN submission succeeds, THE MCP_Server SHALL poll `GET /api/olive/agent/status/:jobId` at a fixed 2-second interval until a Terminal_State is reached or the effective timeout expires; WHILE the job status is any non-terminal value (including `"pending"`, `"running"`, `"setting_up"`), THE MCP_Server SHALL continue polling
6. IF the job status becomes `"failed"` or `"cancelled"`, THEN THE MCP_Server SHALL stop polling immediately and return the full log dump (up to 200 lines) and error details in the structured response
7. IF the effective timeout expires before a Terminal_State is reached, THEN THE MCP_Server SHALL stop polling and return the last known status with `"timed_out": true` and all logs collected up to that point
8. IF a Terminal_State is reached at the exact moment the timeout expires, THE MCP_Server SHALL report the terminal state with `timed_out: false` (terminal state takes precedence over timeout)
9. WHEN a Terminal_State is reached, THE MCP_Server SHALL return a structured response containing: `status` (string), `job_id` (string), `exit_code` (integer or null), `logs` (list of strings, maximum 200 entries), `metrics` (object or null), `elapsed_ms` (integer), `artifact_path_refs` (list of basename-only strings), `timed_out` (boolean, false), and `side_effect: true`
10. THE MCP_Server SHALL enforce a hard timeout ceiling of 1800 seconds (30 minutes); IF the user-provided timeout exceeds 1800 seconds, THEN THE MCP_Server SHALL clamp the effective timeout to 1800 seconds without returning an error
11. WHEN the timeout parameter is omitted, THE MCP_Server SHALL default to 600 seconds (10 minutes)
12. IF the user-provided timeout is less than 10 seconds, THEN THE MCP_Server SHALL clamp the effective timeout to 10 seconds without returning an error

### Requirement 2: execute_and_observe Tool — Registration and Safety

**User Story:** As a platform maintainer, I want execute_and_observe to be properly registered and marked as side-effecting, so that agents and proxies handle it safely.

#### Acceptance Criteria

1. THE Tool_Import_Registry SHALL contain an entry `"execute_and_observe"` pointing to `("olive_mcp_server.tools.agent_execute", "execute_and_observe")` in the `_TOOL_IMPORTS` dictionary in `olive-mcp-server/olive_mcp_server/mcp_server.py`
2. THE Allowed_Tools_Set SHALL contain `"execute_and_observe"` in `src/server/services/mcp/allowedTools.ts`, listed under a Phase 3 agent autonomous loop comment group
3. WHEN `execute_and_observe` returns a successful result (job submitted), THE response dictionary SHALL include the field `"side_effect": true`; WHEN the tool returns an error before submission occurs (invalid input, policy denial, studio unavailable), the response SHALL NOT include the `side_effect` field
4. THE MCP_Server SHALL lazy-import the `execute_and_observe` tool module via `importlib.import_module` at first invocation — the module file SHALL NOT execute network I/O, subprocess calls, or import packages outside the Python standard library and the project's own `olive_mcp_server` namespace at module-load time
5. IF the `execute_and_observe` tool module fails to import at invocation time (e.g., `ImportError`), THEN THE MCP_Server SHALL return `{"error": "internal_error", "message": "..."}` without raising an unhandled exception

### Requirement 3: plan_optimization Tool — Intent to UIState Patch

**User Story:** As an autonomous agent, I want to describe my optimization intent in natural language and receive a ready-to-apply UIState patch, so that I can configure the pipeline without manually composing pass settings.

#### Acceptance Criteria

1. WHEN a natural language intent string of 1 to 2000 characters is provided, THE MCP_Server SHALL return a UIState_Patch containing zero or more of the following fields: `modelSource`, `hfModelId`, `ihvProvider`, `openvinoTargetDevice`, `cudaVersion`, and `passes` (as a partial pass-settings object matching the UIState passes shape)
2. THE MCP_Server SHALL compose the plan by calling the existing `get_quantization_strategy`, `get_hardware_optimization_guide`, and `get_pass_chain` functions directly — reusing their dispatch tables and hardware profile data
3. WHEN an optional `hardware_probe` object is provided, THE MCP_Server SHALL use it to refine provider selection and CUDA version instead of inferring from the intent text alone
4. WHEN an optional `model_id` string is provided (1 to 200 characters), THE MCP_Server SHALL use it for model-type inference (LLM, CNN, Vision, Speech) to select appropriate quantization methods via the existing `_normalize_model_type` classification
5. IF the intent string cannot be parsed into at least one of (target hardware, model reference, or optimization goal), THEN THE MCP_Server SHALL return an error response with code `"unparseable_intent"` and a message indicating which elements could not be identified, without returning a UIState_Patch
6. WHEN Studio is reachable and validation succeeds, THE MCP_Server SHALL validate the generated patch by calling `validate_ui_state_recipe` through the Studio_Bridge and include `"validated": true` in the response without a `validation_note` field
7. IF Studio is unreachable, THEN THE MCP_Server SHALL return the patch with `"validated": false` and a `"validation_note"` string explaining that bridge validation was skipped
8. THE MCP_Server SHALL return a JSON response containing: `ui_state_patch` (partial UIState object), `reasoning` (string explaining choices), `alternatives` (array of 0 to 3 alternative approaches each with `description` and `ui_state_patch`), and `validated` (boolean)
9. THE MCP_Server SHALL declare `plan_optimization` with `side_effect: false` metadata

### Requirement 5: diagnose_and_fix Tool — Error Diagnosis with Recipe Repair

**User Story:** As an autonomous agent, I want to submit an error message and my current recipe, and receive both a diagnosis and a repaired recipe, so that I can auto-recover without human interpretation of workaround text.

#### Acceptance Criteria

1. WHEN an error message string (1 to 4000 characters) and a current recipe object are provided, THE MCP_Server SHALL call the existing `troubleshoot_olive_error` logic internally to produce a diagnosis
2. IF the error message is empty or exceeds 4000 characters, THEN THE MCP_Server SHALL return an error response with code `"invalid_input"` without invoking troubleshooting logic
3. WHEN the diagnosis contains an `updated_config` field and `applyable` is true in the matched KB_Entry, THE MCP_Server SHALL apply it as a JSON Merge_Patch (RFC 7386) onto the provided recipe to produce a `fixed_recipe`
4. IF the diagnosis has no `updated_config` or the matched entry is null, THEN THE MCP_Server SHALL return `fixed_recipe: null` and `fix_confidence: "none"`
5. WHEN a fixed recipe is produced and Studio is reachable, THE MCP_Server SHALL validate the fixed recipe through `validate_optimization_job` and set `"recipe_validated": true`
6. IF Studio is unreachable during validation, THEN THE MCP_Server SHALL return the fixed recipe with `"recipe_validated": false`
7. THE MCP_Server SHALL return a response containing: `diagnosis` (the full troubleshoot result object), `fixed_recipe` (object or null), `changes_made` (list of human-readable change descriptions), `recipe_validated` (boolean), and `fix_confidence` (one of `"high"`, `"medium"`, `"low"`, `"none"`) — where `"high"` means KB entry matched with `updated_config` present, `"medium"` means KB entry matched but fix was rule-based inference, `"low"` means weak KB match, `"none"` means no fix could be determined
8. WHEN an optional `hardware_probe` object is provided, THE MCP_Server SHALL pass it to the troubleshooting context for hardware-aware diagnosis
9. THE MCP_Server SHALL declare `diagnose_and_fix` with `side_effect: false` metadata

### Requirement 7: compare_results Tool — Multi-Job Comparison

**User Story:** As an autonomous agent, I want to compare multiple job results side-by-side with a scored recommendation, so that I can select the best optimization variant without manual analysis.

#### Acceptance Criteria

1. WHEN a list of 2–10 job_ids and a preference string are provided, THE MCP_Server SHALL fetch results for each job via the Studio_Bridge status endpoint
2. IF fewer than 2 or more than 10 job_ids are provided, THEN THE MCP_Server SHALL return an error with code `"invalid_job_count"` and a message stating the 2–10 range requirement
3. WHEN the preference parameter is one of `"latency"`, `"size"`, `"accuracy"`, or `"balanced"`, THE MCP_Server SHALL score each completed job accordingly and select the highest-scoring as winner
4. IF preference is not one of the valid values, THEN THE MCP_Server SHALL default to `"balanced"`
5. IF a job is not in a Terminal_State, cannot be fetched, or has status `"failed"`, THEN THE MCP_Server SHALL exclude it from scoring and list it in `excluded_jobs` with the reason
6. IF after exclusions fewer than 2 jobs remain for scoring, THEN THE MCP_Server SHALL return the full response structure with `winner: null`, the `comparison` array containing only the remaining job(s), and `reasoning` explaining insufficient comparable results
7. THE MCP_Server SHALL return a response containing: `comparison` (list of per-job objects with `job_id`, `status`, `metrics`, and `score`), `winner` (job_id string or null), `reasoning` (string explaining the selection), `excluded_jobs` (list of `{job_id, reason}` objects), `preference` (the effective preference used), and `side_effect: false`
8. WHEN the preference is `"balanced"`, THE MCP_Server SHALL weight available metrics equally; WHEN a specific preference is chosen, that metric SHALL receive 2x weight relative to others in scoring

### Requirement 9: get_model_info Tool — Model Metadata Lookup

**User Story:** As an autonomous agent, I want to look up model metadata by HuggingFace ID, so that I can make informed planning decisions about quantization and VRAM requirements.

#### Acceptance Criteria

1. WHEN a `model_id` string of 1 to 256 characters is provided, THE MCP_Server SHALL attempt an HTTP GET to `https://huggingface.co/api/models/{model_id}` with a 3-second timeout using `urllib.request`
2. IF `model_id` is empty or exceeds 256 characters, THEN THE MCP_Server SHALL return an error with code `"invalid_model_id"` without making an HTTP request
3. WHEN the HF API returns HTTP 200, THE MCP_Server SHALL extract: parameter count (from `safetensors.total` or `config.num_parameters`), architecture (from `config.architectures[0]`, defaulting to `"unknown"`), and compute VRAM estimate as `params_b × 2` GB (FP16 baseline)
4. IF the HF API call fails (timeout, 404, network error) or the response lacks extractable parameter count, THEN THE MCP_Server SHALL fall back to regex heuristics porting the `inferParamBillions` logic from `src/lib/vramEstimate.ts`
5. THE MCP_Server SHALL return: `params_b` (float), `architecture` (string), `model_type` (one of `"llm"`, `"cnn"`, `"vision"`, `"speech"`, `"generic"`), `estimated_vram_gb` (float), `recommended_quant` (`"int4"` when params_b ≥ 6.0, otherwise `"int8"`), `source` (`"huggingface_api"` or `"heuristic"`), and `confidence` (`"high"`, `"medium"`, or `"low"`)
6. WHEN source is `"huggingface_api"`, confidence SHALL be `"high"`
7. WHEN source is `"heuristic"` with explicit size token match (e.g. "7B"), confidence SHALL be `"medium"`; for family-based defaults, confidence SHALL be `"low"`
8. THE MCP_Server SHALL declare `get_model_info` with `side_effect: false` metadata and use no new pip dependencies

### Requirement 11: Startup Performance Preservation

**User Story:** As a platform maintainer, I want all new tools to maintain the MCP server's fast startup, so that agent sessions remain responsive.

#### Acceptance Criteria

1. THE MCP_Server SHALL lazy-import all 5 new tool modules via `importlib` entries in `_TOOL_IMPORTS` — no module-level imports of network libraries, `numpy`, `sentence-transformers`, or any non-stdlib package in the new tool files
2. WHEN the MCP_Server process starts and no tool has been called, none of the 5 new tool module paths SHALL be present in `sys.modules`
3. THE MCP_Server SHALL add no new entries to `pyproject.toml` `[project.dependencies]` — all 5 tools use only Python stdlib (`urllib.request`, `json`, `time`, `re`, `typing`) and existing internal packages (`studio_loopback`, `troubleshooting`, `strategy_advisor`, `hardware_guide`, `pass_chain`, `compatibility`)
4. IF a lazy-imported new tool module fails to resolve on first call, THEN THE MCP_Server SHALL return an error response without crashing the server process or affecting other tools

### Requirement 12: Error Handling Consistency

**User Story:** As an autonomous agent, I want all new tools to return structured errors in the same format as existing tools, so that my error-handling logic remains uniform.

#### Acceptance Criteria

1. THE MCP_Server SHALL return every error as a JSON object containing at minimum `"error"` (non-empty string, snake_case code) and `"message"` (non-empty string); an optional `"detail"` field MAY be included for diagnostic context
2. WHEN Studio is unreachable, THE MCP_Server SHALL return `{"error": "studio_unavailable", "message": "...", "detail": "..."}` using the existing `studio_unavailable()` helper from `studio_loopback.py`
3. WHEN a job_id fails validation against the pattern `^[A-Za-z0-9_-]{1,128}$`, THE MCP_Server SHALL return `{"error": "invalid_job_id", "message": "..."}` using the existing `err()` helper
4. WHEN a bridge response is malformed (not a JSON object or missing required fields), THE MCP_Server SHALL return `{"error": "invalid_bridge_response", "message": "..."}` matching the existing pattern
5. IF an unexpected exception occurs in any new tool function, THEN THE MCP_Server SHALL catch it and return `{"error": "internal_error", "message": "<ExceptionClassName>: <message>"}` — the tool function SHALL NOT propagate the exception to the MCP framework; IF the catch mechanism itself fails, THE MCP framework's top-level handler SHALL convert any propagated exception to `{"error": "internal_error", "message": "..."}` format
6. WHEN an exception occurs during a categorized operation (Studio connectivity, job_id validation, bridge response parsing), THE MCP_Server SHALL return the specific error code for that category (`studio_unavailable`, `invalid_job_id`, `invalid_bridge_response`) rather than the generic `internal_error` — the generic `internal_error` code is reserved for truly unexpected exceptions not covered by a specific category
7. IF multiple error conditions apply simultaneously, THEN THE MCP_Server SHALL return the error for the first failing validation in parameter-check order (input validation before network errors)

### Requirement 13: Test Coverage

**User Story:** As a developer, I want dedicated test files for each new tool with mocked externals, so that CI can validate the tools without Studio or network access.

#### Acceptance Criteria

1. THE test suite SHALL contain `tests/test_agent_execute.py` covering execute_and_observe with mocked `studio_request` simulating: successful completion (returns final metrics and logs), failed job early abort (stops within 1 poll cycle), timeout expiry, submission denied (403), and studio unavailable
2. THE test suite SHALL contain `tests/test_agent_planner.py` covering plan_optimization with mocked internals simulating: LLM intent parsing, CNN intent parsing, intent with hardware_probe, Studio-down degradation (validated: false), and unparseable intent error
3. THE test suite SHALL contain `tests/test_agent_diagnosis.py` covering diagnose_and_fix with mocked troubleshoot logic simulating: KB match with updated_config (recipe patched), KB match without updated_config (fixed_recipe: null), no KB match, and bridge validation unavailable
4. THE test suite SHALL contain `tests/test_agent_compare.py` covering compare_results with mocked job fetches simulating: 2+ completed jobs comparison, excluded non-terminal jobs, insufficient results error, and preference-based scoring differences
5. THE test suite SHALL contain `tests/test_agent_model_info.py` covering get_model_info with mocked urllib simulating: successful HF API response parsing, timeout fallback to heuristic, 404 fallback to heuristic, and invalid model_id error
6. ALL test files SHALL run without network access and without `OLIVE_STUDIO_API_URL` set — all external dependencies monkeypatched
7. FOR ALL new tool functions, serializing output to JSON and parsing back SHALL produce a value-equal object (round-trip property)
