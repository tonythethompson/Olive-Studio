# v0.1 Release Prep — Incremental Changes (Unstaged + Staged Context)

This review covers the unstaged working-directory diff (5 files, ~80 net lines) sitting on top of the earlier staged release-prep commit. The unstaged changes fix credential leakage from localStorage persistence, add a QNN execution gate bypass for preparation mode, introduce an Olive process heartbeat, update tests for the default-model change, apply formatting cleanup to `pipelineValidation.ts` and `jobRunner.ts`, and replace old screenshots in the README.

Watch for: The heartbeat timer has a narrow race where `job.status` transitions to `"cancelled"` but the process hasn't emitted `close` yet — the timer ticks fire into that gap and append log lines to a cancelled job (confirmed). The `partialize` stripping works correctly but does NOT trigger a rewrite of already-stored localStorage data from before this commit (likely stale credentials persist until the user modifies state). Formatting-only changes to `pipelineValidation.ts` alter indentation of `sanitizePipelineState` in a way that reverses the original alignment convention, introducing a style inconsistency (confirmed).

**Verdict**: APPROVED

## High-level view

The QNN execution gate fix introduces a second path that allows "Execute Live" when `probe?.qnn?.loadable === true`, even when QNN is not in `detectedProviders`. This is correct for x64 preparation mode where QNN is not a detected local accelerator (the staged changes already removed x64 from `computeQnnCompatibleHardware`), but the runtime can still run Olive for context binary generation.

The localStorage persistence credential strip (`azureStr: ""`) is now applied in both `partialize` (write path) and `merge` (read path), creating a double barrier. Sessions that rehydrate old localStorage data from before this commit will still see the raw credential in storage until a state write occurs — the merge guard catches it on read so it never surfaces in the application.

The heartbeat timer cleans up on `close` and `error` events and has an internal status guard. The cancel path works through SIGKILL which triggers `close`, so the timer is cleared. There is one low-severity timing window during cancellation where the heartbeat may fire between the status transition and the process exit, but the worst case is one extra informational log line on an already-terminal job.

The recipe catalog collapse (staged) stores expanded groups in a `Set<string>` in React local state, starting empty. Groups render only when expanded. This doesn't affect existing recipe-apply behavior since `applyCuratedRecipe` operates on the item directly, not on group visibility state.

## QNN preparation-mode execution gate

The staged commit already narrowed `computeQnnCompatibleHardware` to return `false` for `hostMode === "preparation"` (Windows x64), so QNN no longer appears in `detectedProviders` for x64 hosts. But the Olive workflow CAN still run on x64 for context binary generation (cross-compile preparation). The unstaged fix in `getLocalExecutionIssues` adds:

```typescript
const qnnPreparationAllowed =
  provider === "QNNExecutionProvider" && probe?.qnn?.loadable === true;
if (!detected && !qnnPreparationAllowed) { ... }
```

If QNN isn't detected (it won't be on x64 after the staged fix), but the runtime probe confirms `qnn.loadable === true`, the "platform-local-execution-unavailable" critical issue is skipped. `loadable` reflects that the venv has the QNN runtime installed and functional — the actual prerequisite for running Olive in preparation mode.

The interaction with DML is unrelated. DML is classified as `"local"` (not `"platformLocal"`), so `getLocalExecutionIssues` takes the detected-providers path for DML, which benefits from the staged `mergeDetectedProviders` fix that now passes `os` and adds DML on Windows hosts via `computeDirectMlHardwareReady`. No false-negative overlap between the two fixes.

## localStorage persistence credential stripping

```typescript
partialize: (store) => ({
  state: {
    ...store.state,
    azureStr: "",
    activeJobId: null,
    localFiles: [],
  },
}),
```

Zustand's persist middleware calls `partialize` on every write to produce the serializable snapshot, so the credential never reaches `localStorage.setItem`. The `merge` side mirrors this with the same three fields zeroed, catching any data that was written before this code was deployed.

One field worth noting: `localFiles` strip is necessary because `File` objects can't serialize to JSON. `activeJobId` is runtime-only (the job won't exist after page reload). `hfDataset` and `hfTask` are retained — they're non-sensitive public identifiers.

The upgrade gap: if a user stored state before this commit with a real `azureStr` value, that raw credential remains in `localStorage` as bytes until the next `setState` call triggers a write through the new `partialize`. The `merge` guard prevents it from entering the application on rehydrate, but it persists in browser storage.

## Heartbeat timer lifecycle

Cleared in:
- `proc.on("close")` — normal exit, failure, or SIGKILL from cancel
- `proc.on("error")` — spawn failure (ENOENT, permission denied)

Internal guard: `if (job.status !== "running") { clearInterval(heartbeatTimer); return; }` — self-clears if status changed between ticks.

Cancel path: `state.ts` sets `job.status = "cancelled"` then calls `proc.kill("SIGKILL")`. SIGKILL delivers `close` which fires `clearInterval`. The heartbeat interval is 15s, so the race window between status change and `close` event is sub-millisecond in practice. Even if the timer fires in that window, the status guard catches it and self-clears. No timer leak possible.

The narrow concern: during that sub-ms gap, if the timer happens to be mid-tick (already past the status guard), it will call `pushLog` with an informational message on a cancelled job. This is benign — `pushLog` doesn't check terminal status and the log array continues to exist until job sweep.

## Recipe catalog collapse behavior

The collapse mechanism uses `expandedRecipeGroups: Set<string>` initialized to empty, so all model groups start collapsed. Applying a recipe via `applyCuratedRecipe` doesn't depend on group visibility — it receives the `item` directly from the row's click handler inside the expanded group.

The EP badges shown in collapsed state (`uniqueDevices`) are derived from the same `rows` data that populates the expanded view, so they can't drift from the actual targets within a group.
