# v0.3 Agent — MCP Knowledge Gap Analysis

> Audited 2026-08-09 against the live MCP server (27 tools, 84+ passes, 22 HW profiles).
> Purpose: identify what's missing from the MCP knowledge layer before the autonomous agent can function.

## Current state: what's sufficient

| Capability | Tools | Depth |
|---|---|---|
| Pass knowledge | `get_olive_passes`, `get_pass_parameters`, `get_pass_config_template` | 84+ passes with full schemas, params, enums, hardware requirements, gotchas |
| Strategy recommendations | `get_quantization_strategy`, `get_hardware_optimization_guide` | Returns algorithm + pass chain + expected outcomes + risks for model x hardware |
| Troubleshooting | `troubleshoot_olive_error`, `diagnose_error`, `get_error_frequency_summary` | 34 Olive + 12 Studio entries with pattern matching and KB feedback loop |
| Validation | `validate_ui_state_recipe`, `get_recipe_for_ui_state` | Full UIState bridge for recipe generation and validation |
| Compatibility | `get_model_compatibility`, `get_pass_chain` | Cross-checks model type x pass x hardware; validates pass ordering |
| Job lifecycle | `submit_optimization_job`, `get_optimization_job`, `get_optimization_results`, `cancel_optimization_job` | Present but require Studio running (`OLIVE_STUDIO_API_URL`) |

## Gaps: what the agent needs but doesn't have

### Gap 1: No "plan from intent" tool (Medium)

**Problem:** Agent can get strategy recommendations but no tool takes a natural language intent ("optimize Llama for RTX 4090, latency <50ms") and returns a complete UIState patch ready to apply.

**Current workaround:** Agent must compose from `get_quantization_strategy` + `get_hardware_optimization_guide` + `get_pass_chain` and build the patch itself.

**Proposed tool:** `plan_optimization(intent: string, hardware_probe: object, model_id?: string) -> { ui_state_patch: Partial<UIState>, reasoning: string, alternatives: object[] }`

---

### Gap 2: No execution observation tool (High)

**Problem:** No tool that watches a running job's SSE stream and returns structured events. The agent must poll `/olive/agent/status` or consume the SSE stream directly from the Express server, which the MCP stdio transport can't do.

**Current workaround:** Agent polls `get_optimization_job` repeatedly (latency + no real-time awareness).

**Proposed tool:** `execute_and_observe(recipe_json: string, timeout_seconds?: number) -> { status, logs: string[], metrics?: object, error?: string, elapsed_ms: number }`

This tool would:
- Submit the job via the Studio bridge
- Poll/watch until completion or timeout
- Return the full outcome as a single structured response
- Include log lines relevant to diagnosis if failed

---

### Gap 3: No error-to-recipe-fix mapping (Medium)

**Problem:** `troubleshoot_olive_error` returns root cause + workaround text but not always a structured recipe modification. The `updated_config` field exists on some KB entries but is sparse.

**Current workaround:** Agent interprets the diagnosis text and modifies the recipe based on its own knowledge of what the workaround means.

**Proposed tool:** `diagnose_and_fix(error_text: string, current_recipe: object, hardware_probe?: object) -> { diagnosis: object, fixed_recipe?: object, changes_made: string[] }`

This tool would:
- Run `troubleshoot_olive_error` internally
- If a fix is deterministic (e.g., "switch to INT8", "enable per_channel"), apply it to the recipe
- Return both the diagnosis and the modified recipe ready for retry

---

### Gap 4: No multi-recipe comparison (Low)

**Problem:** No tool that takes 2+ job results and produces a structured comparison with a recommendation.

**Current workaround:** Agent calls `get_optimization_results` for each job and diffs manually.

**Proposed tool:** `compare_results(job_ids: string[]) -> { comparison: { latency, size, accuracy }, winner: string, reasoning: string }`

---

### Gap 5: Studio connection required (High for dev)

**Problem:** `studio.reachable: false` in capabilities. The bridge-backed tools (`validate_ui_state_recipe`, `get_recipe_for_ui_state`, job lifecycle tools) require `OLIVE_STUDIO_API_URL` set to a loopback URL with Studio running.

**Impact:** During development, the MCP server must be paired with a running Studio instance for the agent to validate recipes or submit jobs. This is fine in production (Studio is always running) but complicates isolated MCP testing.

**Fix:** Set `OLIVE_STUDIO_API_URL=http://127.0.0.1:3000` in the MCP server environment when Studio is running. Already documented but not automatic.

---

### Gap 6: No model metadata lookup (Low)

**Problem:** No tool that takes a HuggingFace model ID and returns parameter count, architecture, typical VRAM requirements. The VRAM estimation logic is client-side only (`src/lib/vramEstimate.ts`).

**Current workaround:** Agent infers from model name patterns (the same `inferModelType` logic that exists client-side).

**Proposed tool:** `get_model_info(model_id: string) -> { params_b: number, architecture: string, estimated_vram_gb: number, recommended_quant: string }`

---

## Priority for v0.3 implementation

| Priority | Tool | Reason |
|---|---|---|
| 1 | `execute_and_observe` | Core autonomous loop: can't iterate without watching outcomes |
| 2 | `plan_optimization` | Intent-to-action: the entry point for the agent workflow |
| 3 | `diagnose_and_fix` | Auto-recovery: closes the retry loop without human interpretation |
| 4 | `compare_results` | Nice-to-have: enables "try both and tell me which is better" |
| 5 | `get_model_info` | Nice-to-have: improves planning accuracy for unknown models |

## What doesn't need to change

- The knowledge layer (passes, hardware profiles, compatibility matrix, troubleshooting KB) is deep enough
- The existing 27 tools remain the foundation; new tools compose on top of them
- The UIState flat bag works fine as the agent's interface (MCP bridge handles domain logic)
- The circuit breaker, batching, and tool dispatch architecture are solid
